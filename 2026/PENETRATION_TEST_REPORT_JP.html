エグゼクティブサマリー

緊急

VS-01 — 商品検索のSQLインジェクション

影響を受けるルート GET /sqli?search=

アプリケーションは、searchパラメーターをSQL文へ直接連結しています。そのため、クライアントが送信した構文がSQLiteによってSQLとして解釈されます。

確認内容

次の恒真条件により、4件すべての商品が返されました。

' OR 1=1 --

次のUNIONクエリにより、Injectedという攻撃者が制御する結果行が挿入されました。

' UNION SELECT 999,'Injected','Controlled row',1 --

影響

攻撃者は検索フィルターを回避し、データベース接続から参照可能な情報を読み取れます。データベースの権限によっては、データの変更や削除、認証回避、サービス妨害につながる可能性もあります。

対策

const rows = db
  .prepare('SELECT id, name, description, price FROM products WHERE name LIKE ?')
  .all(`%${search}%`);

パラメーター化クエリと最小権限のデータベースユーザーを使用してください。引用符、コメント記号、論理式を入力しても検索文字列として処理されることを自動テストで確認してください。

高

VS-02 — IDORおよび無制限の注文列挙

影響を受けるルート GET /idor?as=&order_id=

注文の取得時に所有者が検証されません。asパラメーターによって信頼できる認証なしに表示上のユーザーを変更でき、注文ID 0を指定するとすべての注文が返されます。

確認内容

GET /idor?as=alice&order_id=2001
GET /idor?as=alice&order_id=0

AliceとしてBobの注文を参照できました。全件取得では4件の注文が返され、注文#3001、所有者meow、商品Catnip、合計¥10,000、配送先Yokohamaも含まれていました。

影響

攻撃者は他ユーザーの注文内容と配送情報を取得できます。連番のIDによって対象を推測しやすく、特殊値のゼロによって注文全件を一度に取得できます。

対策

const order = db
  .prepare('SELECT * FROM orders WHERE id = ? AND owner = ?')
  .get(Number(orderId), authenticatedUser);

信頼できるサーバー側セッションからユーザーを識別し、注文ごとの所有権を検証してください。ゼロIDによる全件取得を削除し、存在しない注文と権限のない注文には同一の汎用レスポンスを返してください。

中

VS-03 — 反射型クロスサイトスクリプティング

影響を受けるルート GET /xss?q=

qパラメーターが出力エンコードされずにHTMLへ挿入されます。次のペイロードが結果要素内へそのまま返されることを確認しました。

<img src=x onerror=alert(document.domain)>

影響

細工されたリンクを別のユーザーが開くと、VulnShopのオリジン上でJavaScriptを実行できます。実運用アプリケーションでは、被害者が利用できる操作やデータへのアクセスにつながります。

対策

result = `<div class="result">Showing results for
  <strong>${escapeHtml(query)}</strong></div>`;

出力先のコンテキストに適したエンコードを適用してください。追加の防御として、制限の厳しいContent Security Policyも設定してください。

低

VS-04 — データベースエラー情報の開示

不正な検索入力によって発生したSQLiteのエラーがクライアントへ直接返されます。単一の引用符を入力すると、画面上にDatabase errorが表示され、クエリの解析動作を攻撃者が把握できます。

対策

詳細なエラーはサーバー側のみに記録してください。クライアントには一定の汎用メッセージと内部照合用IDを返してください。

情報

VS-05 — ブラウザー防御ヘッダーの不足

X-Content-Type-Options: nosniffは設定されていますが、Content Security Policyおよびフレーム表示を制限するディレクティブはありませんでした。

対策

XSSの原因を修正した後、制限の厳しいContent Security Policyを設定してください。フレーム表示の制御にはCSPのframe-ancestorsディレクティブを使用してください。

評価手法

エンドポイントの探索、パラメーター改変、反射入力の分析、オブジェクト単位の認可検証、SQLメタ文字とUNIONクエリのテスト、レスポンスヘッダーの確認、対象を絞ったソースレビューを実施しました。能動的なテストはすべて127.0.0.1:8000とインメモリの初期データに限定しました。

制限事項

本評価は現在のHTTPルートとソースコードを対象としています。このローカルラボには該当するコンポーネントが存在しないため、展開基盤、TLS、外部依存関係、永続化層、認証済みセッション管理は対象外です。XSSのブラウザー実行は、未エンコードのレスポンスと標準的なHTML動作から判断しました。外部システムはテストしていません。

推奨する修正順序

  1. SQL文字列の連結をパラメーター化クエリへ置き換える。
  2. 信頼できる認証と注文ごとの所有権検証を実装し、order_id=0の動作を削除する。
  3. 反射される出力をエンコードし、制限の厳しいContent Security Policyを設定する。
  4. クライアントへ表示されるデータベースエラーを汎用レスポンスへ置き換える。
  5. 主要3脆弱性に対する自動回帰テストを追加する。
